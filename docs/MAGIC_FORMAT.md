# `.magic` formats v1–v5 and player engineering

This is developer documentation. User instructions are in the desktop README and `web_player/README.md`.

## Archive contract

A `.magic` file is a seekable **ZIP_STORED** archive: no ZIP-level compression, encryption, split disks, ZIP64 or data descriptors. PNG assets use their usual internal PNG encoding. Since application v2.4.5, new exports default to 256 kbps MP3; users can choose 128, 192 or 320 kbps MP3, or PCM16 stereo 44.1 kHz WAV. MP3 compression applies inside the audio entry, while the ZIP container remains stored. Export writes a private temporary archive beside the destination, rechecks all inputs, then publishes it atomically. Existing exports require explicit overwrite selection. The original audio, prepared instrumental, PDF, GP and reviewed timeline are never edited.

| Manifest version | Score contents | Embedded audio |
|---|---|---|
| `1` | PDF, or a legacy selected GP part | `audio/instrumental.wav` |
| `2` | All-part GP | `audio/instrumental.wav` |
| `3` | PDF or all-part GP | `audio/instrumental.mp3` |
| `4` | PDF or all-part GP, shared by all listening versions | One to 15 `audio/variants/<id>.mp3` or `.wav` entries |
| `5` | Same shared score/timing contract | One to 128 complete audio versions, including canonical combined removals |

Application 3.0.0 adds format 4 for an explicit selection of listening versions, including a single selected version. Legacy export requests without `audio_variants` retain their existing output: format 3 for MP3, format 1 for PDF/WAV and format 2 for all-part GP/WAV. Formats 1–3 remain readable and are not migrated automatically. A format 4 file requires player 3.0.0 or later. MP3 support first shipped in an updated v2.4.5 player build. Version 2.4.9 added centered PDF/GP following while preserving the explicit playback-session setup introduced in v2.4.7 and the audio-activation-independent loading introduced in v2.4.6. Earlier different builds all displayed 2.4.5, so that label alone does not establish format 3 support. Use the web update controls described below; an older page without those controls first needs an online launch and refresh or full close/reopen. Do not promise a particular update error from an already deployed reader: its path allowlist can reject a new audio path before checking the manifest version.

Application 3.0.1 changed preparation and playback controls without changing the archive format. Desktop checkboxes prepare several independent fixed variants in one batch; export continues to store each selected version separately. Both players display only available archive choices, including a single choice with its count. The web sidebar can hide while the same live audio-choice and transport elements remain usable above the score. Moving controls or restoring a sidebar preference must preserve decoding transactions, source clocks, Session readiness and explicit playback activation; it must not mutate the manifest or decode additional variants.

Application 3.0.5 makes the normal desktop save workflow include one original mix plus any selected prepared versions in one file. Source grouping continues to use the original file's full SHA-256, including across preparation jobs; equal titles or decoded durations are insufficient. Renaming or moving identical bytes retains the identity, while retagging, editing or re-encoding may change it. The format remains 4 for base entries and 5 for combinations. Readers still accept older archives without an original. This is not an archive-merging operation and never promotes an imported archive's claimed original hash into a trusted separation-cache identity.

| Entry | Meaning |
|---|---|
| `manifest.json` | `format: Magic-Instrumental`, `version: 1`, `2`, `3`, `4` or `5`, title, audio, score, page list, practice defaults, per-entry byte counts and SHA-256 |
| `audio/instrumental.wav` or `audio/instrumental.mp3` | Version-specific audio entry at the current desktop key and original duration; speed is **not** baked into this file |
| `audio/variants/<id>.wav` or `.mp3` | Format 4 listening version; all versions share one original-media time grid and baked key |
| `score/source.pdf` or `score/source.gp3/gp4/gp5` | Unmodified source score |
| `pages/0001.png` … | Prepared display pages, long edge 2200 px, including the selected GP part |
| `timeline.json` | Performed cues, original-media start/end seconds, one offset, reviewed flag, warnings and normalized bar boxes |

For native GP, `score.kind` is `gp`, with selected `track` and `part`. In v1 all pages depict that part. In v2 and GP v3/v4, `parts` lists every track, name, percussion flag, page list and timeline path. The selected reference part uses the root pages/timeline; other tracks use `parts/NN/pages/0001.png` and `parts/NN/timeline.json`. `timing_basis` declares the selected track and `shared: true`. Every part is parsed and its performed source-index/visit/beat/duration route must match the reviewed reference. Only geometry differs; start/end/offset times are shared. Mobile never parses GP or invokes OMR. Switching parts verifies the common time route and preserves transport. A PDF paired with a GP notation source remains a PDF display package. No absolute filesystem paths, cache folder names or full desktop manifests are serialized. Naturally, user-supplied score content and its own metadata remain in the private archive; `.magic` is **not** a public/redacted format.

`audio.pitch_semitones` records the baked desktop shift, ±12. Mobile starts with extra shift 0 and can add ±12; the display reports their sum relative to the original. No printed-note/TAB transposition occurs. `practice` contains quarter-note BPM, meter numerator/denominator and the original-media first-beat origin. Scores may contain repeats and several visits with the same printed number. Loop endpoints refer to performed cue indexes, with inclusive final measure and exclusive media end.

Desktop worker requests also carry optional `expected_sha256`, `expected_source_sha256`, and `expected_frames` per selected variant. When present they must be complete and valid; the exporter verifies prepared bytes against that identity and the actual original recording before pitch work, then checks the canonical frame count. GUI requests always include these fields for pipeline-prepared audio. This prevents a changed cache file from becoming a new trusted export baseline. The fields are request-only, never stored in the portable manifest. Direct API callers supplying their own raw audio paths may omit all three, taking responsibility for those inputs. The existing final hash recheck still rejects changes made during export.

## MP3 metadata and the original PCM time grid

Format 3 adds an explicit compressed-audio contract. Create the current-key, 44.1 kHz stereo PCM representation first, then encode it as MP3. The canonical frame count is measured before MP3 encoding; a frame contains one sample for each channel. Lossy encoding changes sample values, but must not change the original-media coordinate system used by cues, offsets, seeks, loops, pitch metadata or Session.

| `audio` field | Format 3 contract |
|---|---|
| `path` | `audio/instrumental.mp3` |
| `codec` | `mp3` |
| `bitrate_kbps` | Integer `128`, `192`, `256` or `320`; export default `256` |
| `sample_rate` | `44100` |
| `channels` | `2` |
| `frames` | Positive integer number of canonical PCM frames before compression |
| `duration` | Canonical `frames / 44100` seconds |
| `pitch_semitones` | Existing baked desktop key shift |
| `source_sha256` | Existing original-recording identity, independent of the compressed entry hash |

Format 3 accepts the exporter's bounded MP3 profile: no ID3 tag, MPEG-1 Layer III, 44.1 kHz stereo, fixed 128/192/256/320 kbps, and an Info/Xing header with LAME-style encoder-delay and padding metadata. This is the embedded-audio contract, not a general-purpose MP3 importer. Retain that metadata so a compatible decoder can recover the original PCM length.

Before native decoding, the browser walks the actual MPEG frames. It checks every frame's supported rate/channel/bitrate profile, the Info/Xing file-byte and audio-frame counts, and the canonical PCM length calculated from the stream's frame count minus encoder delay and padding. These values must match the manifest and remain within the PCM16-equivalent 512 MiB bound. A falsely short duration or low declared bitrate cannot bypass that bound. Native decoding then separately requires an exact match for decoded frame count, sample rate and channel count. A failed decode or mismatch stops loading with WAV export/browser-update guidance; do not silently shift cue times or accept an altered media duration. Legacy v1/v2 WAV retains its existing PCM validation and requires no added codec fields.

The desktop opens `한 곡을 .magic 파일 하나로 저장` from `PC·태블릿으로 가져가기 · .magic 저장`. `원곡 · 항상 포함` is mandatory; `함께 담을 분리 음원` selects additional prepared versions, initially all checked. Select-all/clear-selection affect only the separated entries. `처음 재생할 음원` chooses either the original or one checked entry; an original-only export is valid. Show `원곡 1개 + 분리 음원 N개 · .magic 파일 하나`. `음질` offers the four MP3 bitrates and `WAV · 무손실`; `저장 위치 선택…` continues to the existing file dialog and overwrite confirmation. Persist the confirmed quality in QSettings `magic_export/audio_quality` as `mp3:128`, `mp3:192`, `mp3:256`, `mp3:320` or `wav`, defaulting to `mp3:256`. Cancelling either dialog or rejecting an overwrite leaves the previous preference unchanged.

The private JSON request for `magic-export --request` adds `audio_format` (`mp3` or `wav`, default `mp3`) and `mp3_bitrate_kbps` (integer `128`, `192`, `256` or `320`, default `256`). Existing input, timeline, key, destination and explicit-overwrite fields retain their meanings. WAV requests can omit the MP3 bitrate field. Do not include the request JSON or its private source paths in a public package.

A lower encoded-audio size does not imply the same reduction for the whole archive: source scores and PNG pages also contribute. Nor does it guarantee lower playback memory. The browser decodes MP3 into PCM before playback, and audio buffers and worklet copies require additional memory. Encoding quality affects new exports only; no background conversion of existing `.magic` files occurs.

## Format 5: prepared combined removals

Application 3.0.2 writes format 5 when any selected audio entry removes multiple targets. It otherwise continues to write format 4 for explicit variants and formats 1–3 for legacy export requests. Format 5 needs desktop/web player 3.0.2 or later. Readers continue to validate legacy format 4 against its original 15-ID contract.

A combined entry has `{id, label, mode, target, targets, audio}`. For example, `{id: "no_vocals_guitar", label: "(보컬 + 기타) 없는 반주", mode: "without", target: null, targets: ["vocals", "guitar"], audio: ...}`. `targets` contains 2–7 unique targets in the fixed order `vocals, guitar, drums, bass, keys, piano, synth`; the ID is exactly `no_` followed by those targets joined with `_`. Reject reordered/duplicate targets, inconsistent IDs, mode/target mismatches, and unknown removal targets. Base entries keep the format 4 schema and must not claim combined metadata. There are at most 128 unique entries per archive, still within the total byte/member limits. Export requests for combinations carry the same `targets` field, along with their prepared byte/source/frame identities.

The embedded combined audio is an actual complete residual prepared on desktop by removing each requested target from the preceding residual. Web and native readers select that single payload; they do not add/subtract independent complete versions. Model estimates from different original-song runs can overlap, and old archives need not contain the original recording or provenance, so readers never invent a combined track from legacy independent mixes. A user who needs a new combination prepares it from the original project and exports it, keeping the existing reviewed score timing.

All format 4 audio-descriptor, common frame grid, source SHA, baked key, shared gain, exact default-audio equality, lazy decoding, failed-switch recovery and Session requirements below also apply to format 5. GP all-part detection includes format 5. Combination labels list every removed target in the chooser, and selections preserve the original clock and practice settings without autoplay.

## Format 4: independent listening versions and score parts

The manifest adds `audio_variants`, `default_audio_variant` and `audio_gain`. Each version is a complete, independently playable mix, not a stem to combine in the browser. The source score, rendered pages, GP part collection and timing are stored once. The audio selector and GP notation selector are independent: choosing the guitar score does not automatically mute or isolate guitar audio.

Each `audio_variants` record has `{id, label, mode, target, audio}`. The list contains one to 15 unique IDs from this fixed table. `label` is nonempty text of at most 100 characters; readers display it with `textContent`.

| `id` | `mode` | `target` | Listening option |
|---|---|---|---|
| `no_vocals` | `without` | `vocals` | Recording with vocals removed |
| `vocals` | `stem` | `vocals` | Isolated vocals |
| `no_guitar` | `without` | `guitar` | Recording with guitar removed |
| `guitar` | `stem` | `guitar` | Isolated guitar |
| `no_drums` | `without` | `drums` | Recording with drums removed |
| `drums` | `stem` | `drums` | Isolated drums |
| `no_bass` | `without` | `bass` | Recording with bass removed |
| `bass` | `stem` | `bass` | Isolated bass |
| `no_keys` | `without` | `keys` | Recording with keyboard-family estimate removed |
| `keys` | `stem` | `keys` | Keyboard-family estimate, including piano and organ |
| `no_piano` | `without` | `piano` | Recording with piano removed |
| `piano` | `stem` | `piano` | Isolated piano |
| `no_synth` | `without` | `synth` | Recording with synthesizer estimate removed |
| `synth` | `stem` | `synth` | Experimental electronic-synth category |
| `original` | `original` | `null` | Original recording |

`keys`, `piano` and `synth` are distinct estimates and can overlap. A synthesizer estimate can include synth bass and electronic percussion; it is not a guarantee of keyboard-player isolation. No reader combines these audio alternatives into an additive mix.

`default_audio_variant` names one listed ID. Top-level `audio` must equal that version's complete descriptor, without extra or omitted fields. Readers must not replace `manifest.audio` when the user changes versions; `MagicArchive.activeAudio` returns the currently selected descriptor, while `activeAudioVariant` contains its identity and label. `audioVariants` normalizes formats 1–3 to one runtime `no_vocals` option without rewriting their manifests.

A format 4 audio descriptor has exactly `path`, `codec`, `frames`, `sample_rate`, `channels`, `duration`, `pitch_semitones`, `source_sha256`, and, only for MP3, `bitrate_kbps`. Its path is `audio/variants/<id>.<codec>`, with `codec` equal to `wav` or `mp3`. The MP3 profile is the same as format 3. WAV uses bounded RIFF PCM16 stereo 44.1 kHz with matching block alignment, byte rate and data-frame count; RF64 and extensible/float WAV are not accepted. All versions must have identical `frames`, `sample_rate`, `channels`, `duration`, `pitch_semitones` and `source_sha256`. Duration is exactly `frames / 44100`. Each canonical PCM16 size is limited to 512 MiB before decoding. Unknown or duplicate IDs, incompatible mode/target pairs, a missing default, differing clocks or a top-level/default mismatch reject the archive before audio decoding.

The explicit `magic-export --request` API takes `audio_variants: [{id, label, mode, target, path}]` and `default_audio_variant`. Each private `path` points to an **untransposed** prepared audio file. The worker applies the common requested `pitch_semitones` through the pitch cache, scans canonical 44.1 kHz stereo **float** audio for sample counts, finite values and peaks, then converts to PCM16 and the selected common MP3/WAV quality. All input hashes are rechecked before atomic publication, and the full archive remains limited to 1 GiB. Do not pass a previously pitched file to this API. A legacy request without `audio_variants` keeps the existing already-pitched `instrumental` argument. Re-exporting an imported archive's baked audio requires a separate explicit policy; it must not silently apply the baked shift twice.

From application 3.0.5, GUI requests additionally set `include_original: true`. The exporter adds or replaces exactly one `original` entry using the actual `audio` source in private staging, without loading a separation model. It shares the selected entries' original SHA, exact frame grid, baked key, quality and common gain. A caller may use `audio_variants: []` with `default_audio_variant: "original"` in this mode. Source and selected-cache validation still apply; a claimed source hash never substitutes for verifying the actual input. Requests omitting the flag retain their previous exact-selection behavior, including older explicit-variant requests and formats 1–3. No reader-side requirement for an original is added. The embedded original is the encoded playback mix, not the source file bytes, and the temporary preparation does not replace the user's source or existing exports.

Float stem/residual outputs can exceed full scale even when the original recording does not. Format 4 prevents silent clipping during PCM16 conversion with **one common attenuation** across every selected version. After pitch and canonical resampling, let `P` be the largest absolute sample across all selected versions. Apply `g = min(1, (32767 / 32768) / P)`; for silence use `g = 1`. There is no per-stem normalization or amplification. The required manifest-level `audio_gain` records this finite linear scalar, `0 < g <= 1`, and the worker reports its attenuation in dB. All embedded samples already include it: web and desktop readers validate and preserve the field but **never apply it a second time**. The exact per-version audio descriptors are unchanged. A single temporary float scan is discarded before measuring the next version, avoiding a collection of full decoded temporary files. MP3 retains its normal lossy encoding behavior; the shared gain specifically prevents saturation of the PCM16 input. Legacy v1–v3 export audio handling is unchanged.

Opening a file decodes only its default audio. Selecting another version pauses at the current original-media position and verifies that version's CRC, SHA, codec profile and native decoded sample count before replacing the working audio. It preserves the GP part, score, current key, speed, loop bounds, count settings, highlight and follow preferences. Old decoded/worklet audio is retired after successful replacement; no decoded-audio list is cached. During switching there can briefly be one working version plus its replacement. A failed switch keeps the previous usable version and its position. No asynchronous switch automatically resumes playback: use explicit Play or Session Ready, including on iPad. Pending worklet setup is cancelled, and audio-generation checks prevent a late old preparation from attaching to the newly selected audio.

The 3.0.5 web UI groups choices under `원곡`, `악기 없는 반주` and `악기만 듣기`, with a `원곡 선택` shortcut using the same switch transaction. Disable the shortcut as `원곡 선택됨` when already selected. A file without `original` keeps its working choices and shows preparation/re-export guidance rather than an invented original entry. Canonical combined labels use parentheses around all removed targets, e.g. `(보컬 + 기타) 없는 반주`. Normalize older stored labels for display from the validated ID/targets without rewriting the manifest or audio. The original shortcut never changes Session readiness or autoplay policy.

In Session, each participant chooses their own audio version and score part. Changing audio clears that participant's readiness and cancels any pending group transport through the existing readiness protocol. They must press Ready again; it does not silently restore readiness after decoding. Original recording SHA and canonical duration keep room identity independent of the local mix. Full GP format 4/5 archives can use the existing file-sharing flow, with the same server size and lifetime limits.

### Desktop import

The desktop imports portable versions 1–5 into a separate cache under `processed/imported-magic/<full archive SHA-256>/v1` by default. From desktop v3.0.4, a configured `Paths.audio_cache` replaces the `processed` prefix. The entire verified audio/page/timing inventory remains together; selecting a separate score-analysis cache does not split an imported bundle or change its manifest. The embedded original-recording SHA is metadata for the media clock; it is not proof that the original audio or separation model cache exists locally. An imported file must not populate or overwrite separation caches indexed by that claimed source hash.

Import validates the bounded archive inventory, member paths, CRC and SHA values before safe extraction and atomic cache publication. Display PDFs and native timeline adapters are built from the included PNG pages and portable timing. No score recognition or audio-to-score alignment is rerun. Imported score bindings use their own namespace and must not write normal original-audio/PDF association links. Switching an imported version preserves its media position and practice settings. It must not invoke a normal fresh-analysis load path that resets the source, key, score, loop or metronome association. The desktop allows imported audio/part selection, extra key and speed changes, and selected-audio WAV/FLAC export. Source analysis, timeline editing and `.magic` re-export are disabled in imported mode; the unchanged original `.magic` remains the portable file.

## Reader limits and trust

Solo and Session expose directly operable native local-file inputs; both deliberately omit `accept`. iPad file pickers can exclude the custom `.magic` extension when it is mixed with the known `application/zip` MIME filter. Both inputs use the same loading path. Do not filter by `File.type` or require an extension rename: browsers may supply an empty or generic MIME type, and the archive reader validates the bytes. The picker and loading corrections require no format migration or re-export of existing bundles. Session's downloaded-file path continues to use the same reader without the local picker.

Since v2.4.6, selecting a file reads and validates the archive, decodes its audio and displays the score without awaiting live audio activation or worklet creation. Previously an indefinitely pending `AudioContext.resume()` could hold `openFile()` before parsing while leaving the input disabled. A file-chooser return does not reliably grant audio activation. Request sound preparation from a direct Play or Session Ready action and bound that wait; failure preserves the loaded song and offers retry. Retiring a worklet must not block opening another file, and stale asynchronous completion must not attach an old song's resources to a new one. Show loading status before asynchronous work and release file-input state on every terminal path. This changes browser lifecycle handling, not the archive schema, audio samples or original-media clock.

The [Web Audio resume algorithm](https://www.w3.org/TR/webaudio-1.0/#dom-audiocontext-resume) can keep the promise pending when starting is not allowed. File-input `change` is not one of HTML's [activation-triggering input events](https://html.spec.whatwg.org/multipage/interaction.html#activation-triggering-input-event). The app bounds resume waiting to four seconds and worklet preparation to fifteen seconds; these bounds release the app's wait, not the browser's underlying promise. File reads, decoding and the initial score display have sixty-second stage limits. A replacement detaches the previous worklet immediately and closes its message port after acknowledgement or one second. Late completion is ignored or disposed after a file change or a failed preparation. Browser tests inject pending resume/cleanup responses while retaining real decoding and subsequent playback.

The browser accepts at most 1 GiB total, 512 MiB per stored audio entry, 15 audio versions in format 4 or 128 in format 5, 200 pages per part, 64 parts, 1,000 total pages, 20,000 unfolded cues and 1,200 archive members. MP3 and format 4/5 WAV check the canonical PCM16-equivalent size against 512 MiB before decoding, using both the declared metadata and the actual supported stream. It checks central/local header agreement, offsets, non-overlap, CRC, uncompressed sizes, a fixed ASCII path allowlist, duplicates and exact member inventory. Manifest/timeline JSON have separate 1 MB/8 MB bounds. Only the active part timeline is retained; all-part GP page and timing paths are an exact inventory in v2/v3/v4/v5, including every declared audio path in v4/v5. It checks cue ordering/pages/geometry, version-specific audio metadata and decoded duration/channels, audio SHA-256, PNG signatures and image dimensions. All labels use `textContent`, images are PNG Blob URLs, and no package-supplied code runs. It never extracts files to disk. Memory-limited devices can fail below these limits; these input bounds are not a guarantee that decoded audio fits a device's available RAM.

Source files are preserved in the package for portability but are not executed or parsed by mobile. They have ZIP CRC and manifest SHA-256 metadata; only assets actually opened by the reader undergo content verification at playback load. A checksum detects corruption, not an authenticated publisher.

## Original time, audio scheduling and count-in

v2.4.7 requests the optional `navigator.audioSession.type = 'playback'` from explicit Play, metronome-on and Session Ready actions before their first asynchronous wait. Feature-detect and guard both access and assignment; absent or unsupported API behavior must not prevent the normal Web Audio path. File reading still does not activate audio. The app previously omitted this declaration. [WebKit describes](https://bugs.webkit.org/show_bug.cgi?id=252746#c2) its ambient Web Audio policy and device mute behavior; the [Audio Session draft](https://www.w3.org/TR/audio-session/) defines `playback` for media audio. This makes the intended category explicit, but browser graph output does not establish sound at an iPad speaker or prove a particular user's mute/output-route state. Keep device verification distinct and preserve the foreground-only pause policy.

Audio preparation always requests `resume()` with a four-second bound, including an already `running` context. It also waits up to one second for finite `currentTime` to advance. If that clock remains stopped, attempt `suspend()` for at most one second, report the failure and let the next direct Play/Ready action retry. Preserve the archive, part, original-media position and practice settings. Advancing clock time proves only clock progress, not audible physical output. Background/pagehide pauses the transport, cancels readiness and suspends the context. The `audioGeneration` guard invalidates audio/Session requests that finish after that transition, including after a quick return to the page. Foregrounding alone does not play the song or restore readiness.

`practice.origin` accepts −30 through 1800 seconds in the archive, the browser and Session transport. A negative value places the first beat before the recording starts. Preserve its value so the beat phase is the same on the desktop and the tablet.

Signalsmith Stretch 1.3.2's embedded WASM runs in an AudioWorklet. `AudioContext.currentTime` anchors each segment `{input, out, rate, end, until}`. Display position is `input + max(0, currentTime - out) * rate`, clipped to the exclusive end. Input time is always original-media seconds. `inputTime` messages from the upstream worklet include lookahead latency and therefore are not the UI's authoritative media clock.

Schedule both the active segment and its inactive end before playback. During a loop, queue the next segment ahead of the boundary; when count-each is enabled, leave an explicit inactive count interval. The generated vendor adapter fixes two upstream scheduling timestamp issues; see the license notice and exact build assertions. Audio spectrum tests verify actual output, not only the app clock.

Period = `240 / (BPM * denominator * rate)` for linked clicks/counts. For N beats and original target beat `b`, start count at `ceil(b) - N`; emit exactly N beats, then enter the track at the unchanged target. Fractional entries shorten the last interval. The same AudioContext schedules click nodes and the music segment. Standalone clicks use an independent origin and rate 1. Seeking/rate/key/meter changes cancel queued events and reanchor once. Gain changes preserve clock phase. Backgrounding deliberately pauses and cancels all queued sounds; no background-playback promise.

## Responsive score and offline app

Desktop GP rendering is pre-analysis only: source SHA + part + GP converter v2 + render v2 + pinned Verovio 6.4.1. Verovio measure IDs and SVG staff bounds provide native geometry; no OCR or PDF geometry guessing is used for this route. The internal PDF is a display artifact. Alignment uses the single original notation part; the displayed TAB duplicate must not double the alignment notes.

v2.4.9 desktop and web viewers stack PDF and GP display pages vertically, with half-viewport padding at both document ends. The center of the full current measure box, including simultaneous staves, is the vertical target at every zoom/viewport size. Retain the complete source page and its margins; measure boxes are not crop bounds for titles, chord symbols or annotations. Visibility of upcoming systems/pages depends on those margins, zoom and viewport height. Consecutive forward measure/system/page transitions within one viewport height move smoothly. Longer moves, explicit seeks, repeats, coda jumps and follow re-enabling return promptly without sweeping through intervening measures. Highlighting is independently optional and remains attached to the active page. Resizing or changing GP parts preserves the original-media clock. The desktop uses existing normalized boxes even when an old pixel camera profile differs. Box-free legacy desktop frames retain their matching camera/page fallback and view-only reanalysis guidance. This display change does not rewrite timings, score sources or portable format versions; existing bundles need no re-export solely for centered following.

Mobile creates continuous page slots from the validated PNG dimensions and loads a bounded set of nearby page Blob URLs. It reuses the current part's normalized measure geometry and does not rerun recognition/alignment. Manual gestures suspend following until the user re-enables it. Page slots preserve their dimensions while images load or are released, keeping scroll coordinates stable. A part/file change must detach old slots and revoke obsolete Blob URLs without letting a late image load update the new score. Reviewed page corrections still override generated geometry; their unknown positions fall back to page bounds.

PDF-only measure/BPM exports use format 5 when combinations are included, format 4 with base explicit audio selections, or legacy format 3 with MP3 / format 1 with WAV. They require no XML source and retain the original full score without part separation. Their portable timeline retains optional `camera_mode: "system"` for compatibility. v2.4.9 centers the full simultaneous-staff box for PDF and GP rather than sweeping through instruments within each measure; the existing enum is still validated and no new field is required. The timing remains fixed BPM/meter or user-reviewed timing, not automatic audio alignment or repeat recognition.

`tools/build_web.py` creates `web_player/index.html` with all JS/CSS/WASM in one file, and a versioned service worker. Initial HTTPS (or localhost during development) is required for PWA installation. The worker caches only the static app, never `.magic` contents. Each launch asks the user to select a local file again. iPad Files HTML previews are not presented as a supported installation route. Solo static hosting needs no server-side code, API, analytics or account. Optional Session mode uses the separately deployed relay described in `SESSION_SERVER.md`; its API responses are never persisted in the app cache.

### Verified updates without reloading a running practice

v2.4.8 preserves the existing revisioned fetch and SHA-256 validation before service-worker installation. Keep automatic `skipWaiting()` and `clients.claim()` after successful installation; the active worker and an already open document can therefore represent different builds. Never infer that the visible document has changed merely because the worker activated, and never reload it automatically. Keep the prior cached app available if a new download fails validation.

## Session scheduling

`ensemble.js` measures WebSocket round trips against the relay's monotonic UTC mapping. `performance.now()` and the lowest-RTT sample estimate the server offset; device wall-clock values are not trusted. The relay chooses a 1–5 second future deadline from the slowest participant's measured RTT and requires acknowledgements from every ready participant. Missing acknowledgements cancel the reservation before the deadline. Sequence numbers invalidate stale commands.

The browser maps the deadline into its running AudioContext. It schedules an inactive boundary and optional new counted segment in advance; UI state changes at the deadline. Existing loop scheduling invalidates/rearms that pending boundary rather than overwriting it. Old metronome events are clipped at the deadline; new count events share the same output clock. Member score switching never changes the shared media clock. Speed/key/meter/loop editing is restricted to a paused leader to avoid competing live clock edits.

Original recording SHA-256 and duration bind room readiness. `audio.source_sha256` was added to new exports; v1 fallback requires identical PCM entry SHA. The absolute original-song key is shared; each device subtracts its own baked key before applying the extra web shift. Different score routes are permitted for separately authored member files, but their reviewed times must use the same original recording coordinates. Room loop endpoints are absolute media seconds, not member cue indexes.

The server enforces leader-only transport independently of the UI. Background/audio suspension, readiness loss, connection loss and room expiry cancel scheduled playback. No audio is streamed between participants. Physical output/Bluetooth latency and long-term audio-clock drift are not calibrated; browser-state timing tests are not measurements of acoustic inter-device synchronization.
